---
title: Rate limits
description: How many requests you can make, and what to send when you call the API from a server.
---

The API has no keys, so limits are applied per IP address and per sender wallet.

| Endpoint | Per IP address | Per sender wallet |
| --- | --- | --- |
| `POST /bridge/quote` | 10 a minute | 10 a minute |
| `POST /bridge/build` | 10 a minute | 10 a minute |
| `POST /bridge/transfers/{id}/submit` | 10 a minute | 10 a minute |
| `GET` endpoints | Not limited | Not limited |

Each endpoint has its own count, so one transfer uses one request from each of the three limits. The sender wallet is the `sender` on the quote, and build and submit count against the same wallet.

## When you hit a limit

The API returns `429` with a `Retry-After` header and `retryAfterMs` in the body. If both the IP and the wallet limit are exceeded, you get the longer of the two waits.

```json
{ "error": { "code": "rate_limited", "message": "too many bridge requests; slow down", "retryAfterMs": 1200 } }
```

To stay under the limits:

- Quote when the user asks for a price, not on every keystroke.
- Build from the `decisionId` you already have. A quote stays valid until its `expiresAt`.
- Wait for `retryAfterMs` before retrying instead of retrying in a loop.

## Calling the API from a server

If your backend calls BRDG for your users, send each user's own IP address as `userIp` on the quote. Two venues, Husher and SideShift, need the end user's IP and are left out of the quote without it, with a reason in `rejected`. `GET /bridge/venues` marks these venues with `capabilities.requiresUserIp`.

BRDG stores `userIp` with the quote and reuses it when you build, so you only need to send it once. If your users call the API directly from their browsers, you do not need to send it.

All requests from your server share one IP address, so the per-IP limit applies to your whole server. Plan your request volume around it.
